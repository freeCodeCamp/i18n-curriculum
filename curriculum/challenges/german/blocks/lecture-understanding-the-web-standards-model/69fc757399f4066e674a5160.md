# --description--

Der Prozess zur Erstellung von Webstandards variiert je nach Organisation. Das W3C betreibt formelle Arbeitsgruppen mit strukturierten Überprüfungsphasen. WHATWG funktioniert eher wie ein Open-Source-Projekt. TC39 hält alle zwei Monate persönliche Treffen ab, bei denen Delegierte darüber abstimmen, ob Vorschläge weiterverfolgt werden. Die Khronos Group beschränkt die Teilnahme je nach Mitgliedschaftsstufe.

Trotz dieser Unterschiede folgt der Prozess, eine Idee in einen Webstandard zu verwandeln, einem erkennbaren Muster.

## 1. Erkennen eines Bedarfs

Standards entstehen aus Reibungen, zum Beispiel wenn Entwickler auf eine Wand stoßen, Browser dasselbe Verhalten auf inkompatible Weise implementieren oder eine neue Fähigkeit von der Plattform einfach noch nicht unterstützt wird. Irgendjemand, irgendwo, ist so frustriert, dass er es aufschreibt. Diese Person kann jeder sein; ein Entwickler, ein großes Unternehmen mit einem Produktbedarf oder ein Ingenieur in einem Browser-Team. Was in dieser Phase zählt, ist nicht Autorität, sondern Beweise und Fragen, ob das Problem real ist und ob genug Menschen darauf stoßen, um die Aufmerksamkeit der Webplattform zu rechtfertigen.

## 2. Vorschlag und erste Diskussion

Die Idee wird informell festgehalten, etwa in einem GitHub-Issue, einem kurzen Dokument oder einem Erklärtext, der das Problem beschreibt und eine mögliche Lösung skizziert. Ziel ist es in dieser Phase nicht, eine fertige Spezifikation zu erstellen, sondern herauszufinden, ob das Problem Anklang findet. Erkennen andere Entwickler es? Haben Browser-Hersteller Interesse? Gibt es eine offensichtliche Lösung oder mehrere konkurrierende? Bei TC39 entspricht diese frühe Phase den Stufen 0 und 1. Im W3C passiert das oft informell in einer Community Group, bevor eine formelle Working Group eingesetzt wird. Die WHATWG handhabt das über offene GitHub-Diskussionen in ihren Kern-Repositories. Der Ort unterscheidet sich, aber die Funktion ist dieselbe.

## 3. Schreiben der Spezifikation

Wenn der Vorschlag an Fahrt gewinnt, muss jemand oder ein kleines Team die eigentliche Spezifikation, oder Spec, schreiben. Eine Spec ist kein Blogbeitrag oder Tutorial, sondern ein präzises, formales Dokument, das genau beschreibt, wie eine Funktion in jeder möglichen Situation funktionieren muss. Randfälle, Fehlerbedingungen, Wechselwirkungen mit bestehenden Funktionen und Sicherheitsaspekte müssen alle bedacht und dokumentiert werden.

## 4. Überprüfung, Einwände und Iteration

Der Entwurf wird veröffentlicht und öffentlich sowie von anderen Browser-Herstellern überprüft. Hier passiert der Großteil der eigentlichen Arbeit. Es werden Einwände erhoben und die Spec wird überarbeitet. Eine Funktion, die eine große Browser-Engine nicht implementieren will, wird selten Standard, egal wie gut sie technisch ist. Der Konsensbildungsprozess kann lange dauern. Manche Vorschläge stocken jahrelang, während Hersteller über Design-Details verhandeln. Andere sterben ganz, wenn klar wird, dass keine Einigung möglich ist.

## 5. Implementierung und Testen

Sobald eine Spec stabil genug ist, beginnen Browser-Hersteller mit der Implementierung. Das startet meist mit einem Feature-Flag, damit die Funktion getestet werden kann, ohne bestehende Nutzer zu beeinträchtigen. Die Implementierung deckt oft Probleme auf, die die Spec nicht vorhergesehen hat, die dann an die Autoren zur Klärung zurückgehen. Eine gemeinsame Test-Suite überprüft, ob jede Implementierung sich tatsächlich gleich verhält. Wenn Chrome, Firefox und Safari alle dieselben Tests bestehen, funktioniert die Spec. Wenn sie abweichen, ist entweder die Spec unklar oder eine Implementierung hat einen Bug.

## 6. Finalisierung

Wenn mehrere unabhängige Implementierungen existieren, die Tests bestanden sind und die Community zufrieden ist, wird der Standard finalisiert. Im W3C bedeutet das den Status einer Recommendation. Bei TC39 heißt das Erreichen von Stufe 4, wonach die Funktion in die nächste jährliche ECMAScript-Version aufgenommen wird. Bei der WHATWG gibt es keinen einzelnen Finalisierungsmoment, der lebende Standard spiegelt einfach den aktuellen Konsens wider und wird kontinuierlich aktualisiert. Der gesamte Prozess kann von wenigen Monaten für eine kleine, unstrittige Ergänzung bis zu über einem Jahrzehnt für etwas Komplexes oder politisch heikles dauern. CSS Grid wurde zum Beispiel erstmals 2011 vorgeschlagen und erst 2017 in allen großen Browsern ausgeliefert. Diese Lücke zwischen einer guten Idee und einem stabilen, universell unterstützten Standard ist der Ort, an dem die meiste Arbeit des offenen Webs still und leise passiert.
