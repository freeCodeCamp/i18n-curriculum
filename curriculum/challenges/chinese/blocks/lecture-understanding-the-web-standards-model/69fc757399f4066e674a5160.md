# --description--

创建 Web 标准的流程因组织而异。W3C 通过正式的工作组和结构化的评审阶段来推进。WHATWG 的运作更像一个开源项目。TC39 每两个月举行一次线下会议，由各方代表投票决定提案是否推进。Khronos Group 则根据成员等级来决定参与权限。

不过，尽管这些流程各有不同，将一个想法变成 Web 标准的过程其实遵循着可观察的模式。

## 1. 识别需求

标准的产生始于摩擦，比如开发者遇到瓶颈，浏览器以不兼容的方式实现相同行为，或者平台根本不支持某项新功能。某个人在某处会因为足够的挫败感而把问题写下来。这个人可以是任何人；开发者、拥有产品需求的大公司，或者浏览器团队内部的工程师。这个阶段重要的不是权威，而是证据和问题：问题是否真实存在，是否有足够多的人遇到它以值得网页平台关注。

## 2. 提案和早期讨论

这个想法通过 GitHub issue、简短文档或解释说明非正式地写出来，描述问题并勾勒可能的解决方案。此阶段的目标不是产出完整的规格说明，而是了解问题是否引起共鸣。其他开发者是否认同？浏览器厂商是否感兴趣？是否有明显的解决方案，或者有几个竞争方案？在 TC39，这个早期阶段对应阶段 0 和阶段 1。在 W3C，这通常在正式工作组成立前的社区组内非正式进行。WHATWG 则通过其核心仓库的公开 GitHub 讨论处理。场所不同，但功能相同。

## 3. 编写规格说明

如果提案获得关注，某个人或小团队必须编写实际的规格说明，简称 spec。规格说明不是博客文章或教程，而是精确、正式的文档，详细描述功能在各种可能情况下必须如何表现。边缘情况、错误条件、与现有功能的交互以及安全性影响都必须仔细考虑并写入文档。

## 4. 审查、反对和迭代

草案会公开发布并由其他浏览器厂商审查。这是大部分实际工作发生的阶段。会提出反对意见，规格说明会被修订。一个主要浏览器引擎拒绝实现的功能，无论技术多么优秀，通常都难以成为标准。这个阶段的共识构建可能耗时很长。有些提案在厂商就设计细节谈判时停滞多年。还有些提案在明确无法达成一致时彻底夭折。

## 5. 实现和测试

一旦规格说明足够稳定，浏览器厂商开始实现它。通常先启用功能标记，这样可以在不影响现有用户的情况下进行测试。实现过程中常会发现规格说明未预见的问题，这些问题会反馈给编辑者进行澄清。共享测试套件用来验证每个实现是否表现一致。如果 Chrome、Firefox 和 Safari 都通过相同测试，说明规格说明有效。如果它们表现不一致，要么是规格说明不清晰，要么是某个实现有错误。

## 6. 定稿

当存在多个独立实现，测试通过，社区满意时，标准就定稿了。在 W3C，这意味着达到推荐状态。在 TC39，这意味着达到阶段 4，之后该功能会包含在下一年度的 ECMAScript 版本中。在 WHATWG，没有单一的定稿时刻，活文档标准持续反映当前共识并不断更新。整个过程可能只需几个月，针对小且无争议的新增功能，也可能超过十年，针对复杂或政治敏感的内容。例如 CSS 网格最初于 2011 年提出，直到 2017 年才在所有主流浏览器中发布。这个从好点子到稳定、被普遍支持的标准之间的差距，是开放网络大部分工作悄然进行的地方。
