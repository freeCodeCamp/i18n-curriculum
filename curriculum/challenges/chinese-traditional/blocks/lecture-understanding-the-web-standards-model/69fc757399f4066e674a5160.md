# --description--

建立網頁標準的流程會因組織而異。W3C 會運作正式的工作小組，並有結構化的審查階段。WHATWG 的運作方式則更像是開源專案。TC39 每兩個月會舉行一次實體會議，由各委派代表投票決定提案是否推進。Khronos Group 則依會員等級來決定參與權限。

然而，這些差異背後，將一個想法轉變為網頁標準的過程，其實有一個可觀察到的樣式。

## 1. 識別需求

標準的起點通常是摩擦，例如開發者遇到瓶頸、瀏覽器以不相容的方式實作相同行為，或是平台尚未支援的新功能。某個人在某處因為這些問題感到足夠挫折而將其記錄下來。這個人可以是任何人；開發者、有產品需求的大公司，或是瀏覽器團隊內的工程師。這個階段重要的不是權威，而是證據和問題：這個問題是否真實存在？是否有足夠多人遇到，值得網路平台關注？

## 2. 提案與早期討論

這個想法會以非正式方式寫成 GitHub 問題、簡短文件或說明文檔，描述問題並勾勒可能的解決方案。此階段的目標不是產出完成的規格，而是了解問題是否引起共鳴。其他開發者是否認同？瀏覽器廠商是否有興趣？是否有明顯的解決方案，或是多個競爭方案？在 TC39，這個早期階段對應於第 0 階段和第 1 階段。在 W3C，這通常在正式工作群組成立前，先在社群群組非正式進行。WHATWG 則透過其核心倉庫的公開 GitHub 討論處理。場域不同，但功能相同。

## 3. 撰寫規格

如果提案獲得關注，某人或小團隊必須撰寫實際的規格（spec）。規格不是部落格文章或教學，而是精確且正式的文件，詳細描述功能在每種可能情況下的行為。邊緣案例、錯誤狀況、與現有功能的互動，以及安全性影響，都必須仔細思考並記錄下來。

## 4. 審查、異議與反覆修正

草案會公開發佈並由其他瀏覽器廠商審查。這是大部分實際工作的所在。異議會被提出，規格會被修訂。若某主要瀏覽器引擎拒絕實作某功能，該功能很少會成為標準，不論其技術優劣。這階段的共識建立可能耗時甚久。有些提案因廠商在設計細節上談判而停滯多年；有些則因無法達成共識而完全流產。

## 5. 實作與測試

當規格足夠穩定時，瀏覽器廠商開始實作。通常先以功能旗標啟動，方便測試且不影響現有使用者。實作過程常會發現規格未預料到的問題，這些問題會回送給編輯者釐清。共用測試套件用來驗證每個實作是否行為一致。如果 Chrome、Firefox 和 Safari 都通過相同測試，代表規格有效；若結果不一致，可能是規格不清楚，或某個實作有錯誤。

## 6. 最終定案

當多個獨立實作存在、測試通過且社群滿意時，標準即告定案。在 W3C，這代表達成 Recommendation（建議）狀態。在 TC39，代表達到第 4 階段，該功能將納入下一年度 ECMAScript 版本。WHATWG 則沒有單一的定案時刻，活文件標準持續反映當前共識並不斷更新。整個過程可能從幾個月（針對小且無爭議的新增功能）到十多年（針對複雜或政治敏感的功能）不等。例如 CSS Grid 最初於 2011 年提出，直到 2017 年才在所有主要瀏覽器中推出。從好點子到穩定且普遍支援的標準之間的這段空檔，是開放網路大部分工作默默進行的地方。
